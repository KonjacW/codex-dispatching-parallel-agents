# 重叠变更集成协议

当多个 Agent 触碰同一文件、同一逻辑区域、共享接口、迁移或配置契约时使用。所有候选变更必须基于共同基线，并先在临时集成副本中组合和验证。

## 重叠处理

| 情形 | 处理 |
|---|---|
| 同文件、不同区域 | 并行生成 patch，在临时副本三方合并或顺序应用 |
| 同文件、同一区域 | 可并行提出候选 patch；自动集成出现冲突即停止，即使恰好无文本冲突也按 `needs-review` 处理 |
| 共享接口、迁移或配置契约 | 主 Agent 先确定接口和不变量；文本可合并仍需语义审查 |

禁止把“最后写入者”作为合并策略，也不要直接在最终工作区逐个试 patch。

## 状态

正常路径：`ready → integrated → validated`

异常路径：`ready/integrated → conflicted`、`integrated → validation-failed`、`integrated → needs-review`、任意阶段 → `blocked`。

恢复出口：`conflicted` 与 `validation-failed` 从 `ready` 重新开始；`needs-review` 回到 `integrated`；`blocked` 补齐信息后回到 `ready`。这些都不是终态。

- `ready`：变更集契约完整，等待应用。
- `integrated`：所有 patch 已在临时集成副本中应用，尚未验证。
- `validated`：临时集成副本通过语义审查和最小验证，可交给主 Agent。
- `validation-failed`：patch 已应用，但最小验证失败，不能交付。
- `needs-review`：文本可合并，但接口、不变量、测试、配置键或迁移顺序存在语义风险。
- `conflicted`：文本或上下文冲突，自动集成停止。
- `blocked`：缺少基线、patch、验证、权限或范围信息。

`needs-review` 是质量门：由 `integrated` 转入；解决语义风险后回到 `integrated` 重新应用与验证，不得直接转为 `validated`。

## 判定优先级

语义风险先于文本合并结果和最小验证结果判定：

1. 变更集应用完成后先做语义审查，再判状态。审查要比对各变更集声明的目标行为与不变量，并列出各方新增或修改的顶层符号：函数、类、常量、配置键、环境变量、路由、迁移号。用 patch 和 diff 文本比对即可，不引入语言专用解析器。
2. 出现下列任一情况即为 `needs-review`，**即使文本合并成功、最小验证全部通过，也优先于 `validation-failed`**：某方声明的不变量被覆盖；同一顶层符号被两个变更集定义（取值相同也算，顺序依赖本身就是风险）；同文件同一区域的候选 patch 虽然恰好没有文本冲突；迁移、配置或接口契约的顺序被打乱。
3. `validated` 的前置是语义审查通过 **且** 最小验证通过，两者缺一不可。最小验证通过不等于 `validated`；验证没有覆盖到被争用的符号不构成免责。
4. 不存在语义风险时才按 `integrated → validated` 推进。判定有疑问时按 `needs-review` 处理，而不是按 `validated`。
5. 写回最终工作区后，任务级最终验证失败时同样记 `validation-failed`，并按写回清单回退；不得因为"已经 `validated` 过"而保留该状态。

## 语义审查留痕

主 Agent 必须留下可审计记录：冲突符号清单（符号名 + 各变更集取值）、被覆盖的不变量、未覆盖的不变量、写回清单（写回了哪些 patch 及写回后的 diff）。这些记录与 `needs-review` 的裁决理由一同保留，供重新派发和回退使用。

## 最小验证的覆盖范围

本协议统一称「最小验证」，即最小相关测试、lint、类型检查或 `git diff --check`；提到"最小测试"时同义。最小验证必须覆盖该变更集声明的目标行为与不变量，而不是"跑一遍现有测试"。声明的不变量没有可执行测试时，必须显式记录"未覆盖"并将状态记为 `needs-review`，不得以现有测试通过为理由交付。

## 集成与回退

1. 记录共同基线、所有原始 patch、声明范围和应用顺序。
2. 创建可丢弃的临时集成副本；在其中三方合并或顺序应用全部 patch。
3. 文本合并成功后标记 `integrated`，再运行最小验证，并按「判定优先级」完成语义审查。
4. 最小验证与语义审查都通过后标记 `validated`；有语义风险时标记 `needs-review`。主 Agent检查实际 diff、接口兼容性和未解决风险。
5. `conflicted`、`validation-failed` 或 `needs-review` 时，丢弃临时集成副本，保留原始 patch、日志和冲突/测试/语义报告；最终工作区保持不变。
6. 根据报告重新派发整合或修复任务，并从共同基线创建新的临时副本。不得复用半集成状态。

只有 `validated` 的结果才可交给主 Agent写入最终工作区。写入后仍需完成任务级最终验证；提交、推送和外部动作不因集成成功而获得授权。写入最终工作区是 `validated` 之后的常规协议动作，按写回清单留痕即可，不需要额外的用户授权；提交、推送、删除等不可逆外部动作仍需单独授权，两者不要混为一谈。

## 轻量化边界

优先使用 Git patch、临时副本和现有测试工具。不要求常驻服务、数据库、实时文件锁、事件总线或语言专用 AST 解析器。文件锁只能防覆盖，不能替代变更集、语义审查和测试。
